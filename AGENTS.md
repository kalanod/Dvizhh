# Инструкции для агентов

## Проект и архитектура

Движж (Dvizh) - приложение для поиска и создания мероприятий, участия в них,
личных списков, календаря и рекомендаций. Основная доменная сущность - мероприятие.
Описание продукта в `about_project.txt` включает планы: не считайте все описанные
возможности реализованными. Проверяйте поведение по коду и тестам.

Стек: React 19, TypeScript, Vite, Tailwind CSS; Python 3.12, FastAPI,
SQLAlchemy, Alembic; gRPC/Protobuf; PostgreSQL, pgvector, MinIO; Docker Compose.
MLflow используется для экспериментов и версий моделей.
Публичный трафик проходит через nginx и web-app к backend; внутренние сервисы
и базы не следует открывать наружу без необходимости.

## Структура и локальные инструкции

- `web-app/` - frontend и прокси `/api`; см. [AGENTS.md](web-app/AGENTS.md).
- `backend/` - основной API, доменная логика, миграции; см. [AGENTS.md](backend/AGENTS.md).
- `auth-api/` - отдельный сервис учётных записей; см. [AGENTS.md](auth-api/AGENTS.md).
- `recommendation-service/` - gRPC-рекомендации; см. [AGENTS.md](recommendation-service/AGENTS.md).
- `database-init/` - повторяемая подготовка ролей и векторной схемы; см. [AGENTS.md](database-init/AGENTS.md).
- `postgres/`, `pgvector/` - образы БД и их инициализация.
- `minio/`, `minio-init/` - файловое хранилище и подготовка bucket.
- `nginx/` - публичная точка входа.
- `mlflow/`, `mlflow-init/` - MLflow, резервное копирование и подготовка хранилищ;
  см. [AGENTS.md](mlflow/AGENTS.md).
- `compose.yaml`, `compose.mlflow.prod.yaml` - конфигурации окружений.

Корневые правила действуют во всём репозитории. Локальные `AGENTS.md` уточняют
их в пределах своей директории. Перед изменением прочитай применимые инструкции.

## Роли агентов Codex

Описания ролей: [reader](docs/agents/reader.md) и [coder](docs/agents/coder.md).
Конфигурации Codex находятся в `.codex/agents/`; модель выбирается в TOML роли.
Перед работой в роли прочитай соответствующее описание и локальные `AGENTS.md`.

- `reader` ищет код, собирает контекст, составляет сводки и проверяет diff без изменений файлов.
- `coder` реализует задачу, запускает подходящие проверки и устраняет подтверждённые ошибки.
- Для задач, которым полезно разделение работы, основной агент поручает reader
  исследование, затем coder реализацию, затем reader проверку итогового diff.
  Простые правки выполняй без обязательного запуска всей цепочки.
- Передавай исполнителю конкретную задачу, область поиска и ожидаемый результат.
  Не поручай нескольким агентам одновременное редактирование одних файлов.
- Reader сообщает о проблемах, coder проверяет выводы и исправляет код;
  отсутствие замечаний reader не заменяет тестирование.

Запрет записи для reader является инструкцией, а не отдельным sandbox:
подагенты Codex наследуют права родительской сессии. Для технического запрета
изменений используй отдельную сессию с правами только чтения.
Примеры запуска и ограничения описаны в [руководстве](docs/agents/README.md).

## Общие соглашения

- Делай изменения в рамках задачи.
- Следуй стилю соседнего кода и конфигурациям инструментов. Не форматируй посторонние файлы. Текстовые файлы сохраняй в UTF-8.
- Python: 4 пробела, `snake_case` для функций и переменных, `PascalCase` для классов, аннотации типов; Ruff настроен на Python 3.12 и длину строки 100.
- TypeScript: `PascalCase` для компонентов и типов, `camelCase` для функций,
  `use...` для хуков. Соблюдай ESLint и существующий стиль файла.
- Проверяй изменённую часть проекта. В итоговом сообщении перечисляй изменения, выполненные проверки и ограничения; не заявляй о запуске непроведённых тестов.

## Команды и зависимости

Из корня: `docker compose up --build` - сборка и запуск всего приложения,

`docker compose build` - сборка образов, `docker compose ps --all` - состояние,

`docker compose logs -f` - логи, `docker compose down` - остановка с сохранением volumes.

Сайт: `http://localhost:8080`, Swagger: `http://localhost:8080/api/docs`.
Запуск Compose применяет миграции и инициализацию БД; учитывай выбранное окружение.

| Каталог | Зависимости | Проверки |
| --- | --- | --- |
| `web-app` | `npm ci` | `npm test`, `npm run lint`, `npm run build` |
| Каждый Python-сервис | `uv sync --locked` | `uv run ruff check .`, `uv run pytest` |

Локальный frontend: `npm run dev` из `web-app`; запуск Python-сервисов описан
в локальных инструкциях. Для хоста нужны Node.js 22+ либо Python 3.12 и uv;
для полного запуска через Docker они на хосте не требуются.

Используй npm с `package-lock.json` и uv с отдельным `uv.lock` каждого сервиса.
Не добавляй lock-файлы других менеджеров. Новые зависимости добавляй только
при необходимости: `npm install <package>` или `uv add <package>` в нужном сервисе;
для инструментов разработки - `npm install -D` или `uv add --dev`.
Изменение манифеста и соответствующего lock-файла должно быть согласованным.
Не обновляй зависимости массово в рамках посторонней задачи.

## Безопасность и данные

- Не добавляй в Git и не выводи в ответы/логи секреты, API-ключи, пароли,
  содержимое `.env`, `.env.production`, локальных конфигураций и дампов.
- Не удаляй volumes, данные или bucket.
- Не выполняй сброс БД без явного
  разрешения. В частности, не используйте `docker compose down -v` как способ исправить запуск.
- Не включай `.venv`, `node_modules`, кэши, `dist`, модели и тестовые данные сборок в изменения.
- Не ослабляй проверки доступа, валидацию и изоляцию сервисов ради прохождения тестов.

## Git и pull request

- Работай в отдельной ветке от актуальной `main`: `feat/<task>`, `fix/<task>`
  или `chore/<task>`. Не переключай ветку с чужими изменениями без согласования.
- Без явного запроса пользователя не выполняй commit, push, merge и создание PR.
  Не применяй `reset --hard`, force push и удаление веток без явного разрешения.
