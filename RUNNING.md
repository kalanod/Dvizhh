# Запуск и разработка

## Запустить весь проект

Нужен только запущенный Docker Desktop. Из корня репозитория:

```shell
docker compose up --build
```

Открыть **http://localhost:8080**. Фронтенд, backend, рекомендации и хранилища
запускаются одной командой. Node.js, npm и Python на компьютере для этого не нужны.
`.env` для локального запуска необязателен: Compose содержит значения по умолчанию.
При необходимости скопируйте `.env.example` в `.env` и измените настройки.

Compose автоматически выполняет все шаги:

1. Собирает React внутри Node-контейнера и готовит nginx со статикой.
2. Запускает PostgreSQL, pgvector и MinIO и ждёт их готовности.
3. `database-init` создаёт или обновляет роль `recsys_reader`, права чтения
   и схему pgvector. `minio-init` создаёт bucket, если его ещё нет.
4. Запускает сервис рекомендаций и backend, который применяет миграции Alembic.
5. После готовности API запускает web-app и внешний nginx.

Это работает и с новыми, и с существующими volumes. Подготовительные контейнеры
`database-init` и `minio-init` штатно заканчивают работу с кодом 0.
Ручные SQL-команды и отдельный запуск Vite не требуются.

Для запуска в фоне можно добавить `-d`:

```shell
docker compose up -d --build
```

## Адреса

| Сервис | Адрес |
| --- | --- |
| Сайт | http://localhost:8080 |
| Проверка API и БД | http://localhost:8080/api/health |
| Swagger | http://localhost:8080/api/docs |
| Консоль MinIO | http://localhost:9001 |

Порт сайта настраивается через `NGINX_PORT` в `.env`, по умолчанию `8080`.
Открывайте сайт по этому адресу; порт `5173` относится только к необязательному
режиму разработки ниже.

## Обновление и остановка

После изменений кода используйте ту же команду `docker compose up --build`:
фронтенд пересоберётся, подготовка БД и миграции выполнятся автоматически.

```shell
docker compose ps --all
docker compose logs -f
docker compose down
```

Остановка через `docker compose down` сохраняет данные в volumes.

## Вход в приложение

Зарегистрируйтесь через интерфейс. Авторизации пока нет: регистрация создаёт
профиль через `POST /api/users`, вход выполняется по ID профиля.
На новой БД заранее созданных пользователей нет.

## Эксперименты и версии моделей

Общий MLflow разворачивается на одном сервере. Программы обучения используют
его HTTPS-адрес и сохраняют эксперименты и версии моделей в одном реестре.
Загрузка модели в RecSys ещё не подключена.

### Сервер

Нужны Linux-сервер, Docker Compose 2.24.4+, домен с DNS-записью и свободные порты
80/443. Caddy получает и продлевает TLS-сертификат; HTTP перенаправляется на HTTPS.

```shell
cp .env.production.example .env.production
chmod 600 .env.production
```

Заполнить `.env.production`: `MLFLOW_DOMAIN` — домен без схемы и пути,
каждый пароль и ключ — отдельное случайное значение, например из
`openssl rand -hex 32`. Для существующих PostgreSQL и MinIO указать их текущие
учётные данные. Файл не добавляется в Git; пустые обязательные значения
останавливают запуск.

```shell
docker compose --env-file .env.production --profile ml up -d --build --wait mlflow-gateway
```

Открыть `https://<MLFLOW_DOMAIN>`. Первоначальный пользователь — `admin`, пароль —
`MLFLOW_AUTH_ADMIN_PASSWORD` (не короче 12 символов). Пользователей и права
на эксперименты и модели администратор настраивает средствами MLflow.
Новые пользователи не получают доступ к чужим данным автоматически.

Пароль администратора из env используется только при первом создании.
Изменение env не меняет пароль существующего пользователя: для этого используется
управление пользователями MLflow. `MLFLOW_FLASK_SERVER_SECRET_KEY` сохраняется
между перезапусками.

Для программы обучения:

```text
MLFLOW_TRACKING_URI=https://mlflow.example.org
MLFLOW_TRACKING_USERNAME=<пользователь>
MLFLOW_TRACKING_PASSWORD=<пароль>
```

Порт MLflow и консоль MinIO в серверной конфигурации не публикуются.
API и файлы моделей защищены штатной авторизацией MLflow, включая обращения
из Docker. Клиентам не нужны ключи PostgreSQL или MinIO.

`mlflow-init` автоматически подготавливает отдельную БД и пользователя `mlflow`,
bucket `mlflow-artifacts` и пользователя MinIO с доступом к нему.
Пользователи и права MLflow хранятся в той же БД, что и эксперименты.
Повторная подготовка и пересоздание контейнеров сохраняют данные в volumes.

Обновление выполняется той же командой `up` после резервного копирования.
Полная остановка проекта без удаления данных:

```shell
docker compose --env-file .env.production --profile ml down
```

### Резервное копирование и восстановление

На сервере с Python 3.12+ и доступом к Docker, из корня репозитория:

```shell
python3 mlflow/backup.py backup /srv/backups/mlflow/snapshot
python3 mlflow/backup.py restore /srv/backups/mlflow/snapshot
```

Команды используют `.env.production`; другой файл задаётся через `--env-file`.
Для каждой копии нужен новый каталог. На время копирования останавливается только
MLflow: его БД и файлы сохраняются одним комплектом с контрольными суммами.
Параллельные операции с тем же env-файлом отклоняются.

`restore` заменяет БД и файлы MLflow; данные приложения и другие buckets
не затрагиваются. PostgreSQL, MinIO, роль и bucket должны быть подготовлены
обычным запуском. При ошибке восстановления MLflow остаётся остановленным.
После успешной операции он запускается, если работал до неё.

Настроить регулярный запуск `backup` и перенос копий за пределы сервера.
Локальная копия не защищает от потери диска. Копии содержат модели и данные
пользователей MLflow; хранить их с ограниченным доступом и шифрованием.
Перед обновлением сохранить комплект: откат миграций выполняется восстановлением
копии с соответствующей версией образа.

### Локальная разработка и проверка

Отдельный локальный стенд без авторизации:

```shell
docker compose --profile ml up -d --build mlflow
```

Адрес — `http://localhost:5000`, порт задаётся через `MLFLOW_PORT`.
Обычный запуск приложения не требует MLflow.

Интеграционная проверка с Docker и Python 3.12+:

```shell
python3 mlflow/tests/test_integration.py
```

Проверка использует серверную конфигурацию и локальный тестовый TLS-сертификат:
доступ к API и файлам, две версии модели, пересоздание контейнера и восстановление
из копии. Данные соседней БД и bucket должны сохраниться.
Отдельный Docker-проект и его volumes удаляются после проверки.

## Необязательно: разработка фронтенда с быстрым обновлением

Обычный запуск выше уже содержит весь фронтенд. Этот режим нужен только для
изменения компонентов без пересборки Docker-образа. Для него нужен Node.js 22+.
При работающем Docker-стеке создайте `web-app/.env.development.local`:

```text
BACKEND_URL=http://127.0.0.1:8080
```

Из `web-app`:

```shell
npm ci
npm run dev
```

Адрес этого отдельного dev-сервера: http://localhost:5173.

## Проверки для разработчиков

Из `web-app`:

```shell
npm ci
npm test
npm run lint
npm run build
```

Из `backend` с Python 3.12 и uv:

```shell
uv sync --locked
uv run ruff check .
uv run pytest
.\test-media.ps1
```

`test-media.ps1` проверяет media/personal API и миграции на отдельных временных
PostgreSQL и MinIO; нужны локальные образы `dvizh-postgres` и `dvizh-minio`.

Из корня репозитория с Python 3.12+:

```shell
python database-init/tests/test_startup.py
python web-app/tests/test_proxy.py
```

Первая проверка использует отдельные PostgreSQL/pgvector и проверяет восстановление
роли, схемы и повторный запуск с сохранением тестовых данных. Нужны образы
`dvizh-postgres`, `dvizh-pgvector`, `dvizh-database-init`, собранные Compose.
Вторая собирает отдельную цепочку nginx → web-app → backend-заглушка и проверяет
SPA-маршруты, query-параметры и лимиты обычных/chunked-загрузок.
Проверки удаляют только собственные тестовые контейнеры и сети.

При локальном запуске backend без Docker команды выполняются из `backend`:

```shell
uv run alembic upgrade head
uv run uvicorn dvizh_backend.main:app --reload --port 8000
```

Добавление зависимости: `uv add package-name`.
