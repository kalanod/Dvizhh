# Учётные записи

`AccountService` — единый бизнес-сервис регистрации, проверки учётных данных,
изменения логина/почты и пароля. HTTP-слой проверяет сессию и источник запроса,
переводит ошибки сервиса в HTTP. `AccountRepository` отвечает за хранение,
а транзакцией управляет request-scoped `Database.session`.
Профили приложения остаются в `backend.UserService`.

`GET /api/auth/username-availability?username=member` — предварительная публичная
проверка никнейма для регистрации и редактора профиля. Использует ту же
нормализацию и ограничения формата, что регистрация; неверный формат даёт 422.
Ответ `{"username":"member","available":true}` содержит только никнейм и флаг,
с заголовком `Cache-Control: no-store`. `AccountService` делегирует индексированный
`EXISTS` репозиторию без чтения пароля, почты и остальных данных аккаунта.
Проверка не резервирует никнейм: уникальность повторно проверяется при сохранении.

`main.py` собирает приложение: lifespan, подключение маршрутов и обработчиков ошибок.
HTTP-маршруты находятся в `api/routers/auth.py`, healthcheck — в `api/routers/system.py`;
схемы запросов и ответов — в `api/schemas/account.py`, обработка ошибок — в `api/errors.py`.

Политика access JWT сосредоточена в `SessionService` (`services/session_service.py`): выпуск и проверка
подписи, алгоритма, issuer/audience, обязательных claims, срока действия и UUID аккаунта.
Сервис принимает токен как строку и возвращает UUID либо `InvalidSessionError`, без HTTP-зависимостей.
Проверка действующей сессии также требует существования аккаунта через AccountRepository.
Маршруты устанавливают и удаляют cookie; HTTP-зависимости извлекают cookie и переводят
ошибку SessionService в 401. Header/origin CSRF-проверки остаются на HTTP-границе.
Регистрация и пароли остаются в `AccountService`: отдельный session-сервис не дублирует эти правила.

Смена пароля из своего профиля проходит по цепочке
UI → `POST /api/personal/password` в backend → `POST /api/auth/password` в auth-api.
Backend делегирует команду и не проверяет и не хеширует пароли.

Тело команды: `current_password`, `new_password` (строки, без обрезки пробелов).
Новый пароль соответствует политике регистрации: `PASSWORD_MIN_LENGTH` (по умолчанию 8)
до 128 символов. Посторонние поля запрещены. Нужны cookie `dvizh_access`,
заголовок `X-Dvizh-Account: 1` и тот же origin при его наличии.
Успех — 204 без тела; неверный текущий пароль — 400 с
`detail: "Invalid current password"`; нет сессии — 401; запрещённый источник — 403;
ошибка формата — 422. Ответы не содержат пароль или хеш.

Сервис блокирует строку аккаунта на время проверки и записи Argon2-хеша,
поэтому параллельная смена не может повторно использовать устаревший хеш.
Уже выданные JWT сохраняют действие до истечения срока; смена пароля меняет
данные для последующих входов, но не завершает существующие сессии.
