# Взаимодействия

## HTTP

Метод: `POST /api/interactions`. Контракт: [dto/interaction.py](src/dvizh_backend/dto/interaction.py).
Маршрут, сохранение и миграции ещё не реализованы.

### Запрос

Объект с непустым массивом `interactions`. Поля каждого действия:

| Поле | Содержание |
| --- | --- |
| `interaction_id` | ID действия, создаваемый Frontend. |
| `item_id` | ID мероприятия; соответствует `events.id`. |
| `event_type` | Действие из таблицы ниже. |
| `timestamp` | Время действия на клиенте с часовым поясом. |
| `session_id` | ID исходной рекомендательной выдачи; необязателен. |
| `request_id` | ID запроса исходной страницы рекомендаций; необязателен. |

Все ID — UUID. `user_id` берётся из авторизации. Лишние поля отклоняются.
Frontend сохраняет пару `session_id` / `request_id` с карточкой, включая переход на её страницу.
Оба ID заполнены либо отсутствуют / равны `null`; вне рекомендаций отсутствуют.
Один пакет может содержать действия из разных страниц.

| `event_type` | Действие |
| --- | --- |
| `IMPRESSION` | Фактический показ карточки. |
| `OPEN` | Открытие страницы мероприятия. |
| `JOIN_CLICK` | Нажатие кнопки записи. |
| `EXTERNAL_LINK_CLICK` | Нажатие ссылки на внешний сайт мероприятия. |

Frontend сообщает эти действия из всех разделов приложения.
Успешные изменения избранного и участия фиксирует Backend.

### Ответ

| Поле | Содержание |
| --- | --- |
| `accepted_interaction_ids` | Все ID пакета без повторов, включая ранее сохранённые действия. |

## Доставка

1. Frontend отправляет действия пакетами; очередь принадлежит аккаунту.
   Удаляет только подтверждённые действия; не отправляет их под другим аккаунтом.
2. Повтор сохраняет все поля. Тот же ID, пользователь и содержимое не создают новую запись.
   Другой пользователь или содержимое с тем же ID отклоняют весь пакет без перезаписи.
3. Backend проверяет и сохраняет пакет в одной транзакции. Ошибка отклоняет пакет
   без новых записей; ответ отправляется после фиксации транзакции.

## Хранение

Таблица — `event_interactions`: `item_id` → `event_id`, `event_type` → `type`,
`timestamp` → `occurred_at`. `session_id` и `request_id` сохраняются без переименования.
Нужно добавить уникальный `interaction_id` и `received_at` — время первого сохранения.
Запоздавшее действие сохраняет исходный `timestamp`; повтор не меняет `received_at`.
Сервис рекомендаций читает взаимодействия из БД Backend для обработки.

## Участие

`JOIN_CLICK` — клик; успешная запись — переход в `GOING` в `participation_status_history`.
Запрос записи передаёт то же действие в поле `interaction`. Backend проверяет
`event_type=JOIN_CLICK` и соответствие `item_id` мероприятию, сохраняет действие
и участие вместе независимо от прихода пакета. Повтор не выполняет операцию заново.

Нужно добавить `participation_status_history.origin_interaction_id` — ссылку на действие.
Одобрение и отмена сохраняют источник попытки записи; повторная запись получает новый
источник без изменения прежней истории.
