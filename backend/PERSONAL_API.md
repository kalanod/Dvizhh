# Основной пользовательский сценарий

API профиля, личных списков, избранного, «Не интересно», дружбы и приглашений.
Все адреса доступны через `http://localhost:8080`; Swagger — `/api/docs`.

## Пользователь и интеграция авторизации

По согласованному временному контракту пользователь передаётся явно:
`user_id` в пути/теле, `actor_id` при приглашении, `viewer_id` при чтении карточек.
Эти идентификаторы НЕ подтверждают личность. Перед публикацией приложения коллега,
реализующий авторизацию, должен получать действующего пользователя из проверенной
сессии и проверять совпадение с личными списками и действиями либо заменить эти
параметры маршрутов на зависимость текущего пользователя.

Проверка ACTIVE-профиля и доменных прав организатора/менеджера уже выполняется
в новых сервисных методах. Политику видимости PUBLIC/FRIENDS/PRIVATE нужно подключить
в рамках отдельной задачи авторизации. Этот этап её не заменяет.
Создание аккаунтов, пароли и `auth-api` в этом изменении не затронуты.

## Маршруты

| Метод | Путь | Назначение |
| --- | --- | --- |
| PATCH | `/api/users/{user_id}` | Частично изменить профиль |
| GET | `/api/users/{user_id}/events?kind=organized` | События, созданные пользователем |
| GET | `/api/users/{user_id}/events?kind=participating` | Участия GOING |
| GET | `/api/users/{user_id}/events?kind=requested` | Заявки REQUESTED |
| GET | `/api/users/{user_id}/favorites` | Избранное |
| PUT / DELETE | `/api/users/{user_id}/favorites/{event_id}` | Сохранить / удалить из избранного |
| GET | `/api/users/{user_id}/dismissed` | Список «Не интересно» |
| PUT / DELETE | `/api/users/{user_id}/dismissed/{event_id}` | Скрыть из персональной ленты / восстановить |
| GET | `/api/users/{user_id}/friends/requests?direction=incoming` | Входящие заявки и профили отправителей |
| GET | `/api/users/{user_id}/friends/requests?direction=outgoing` | Исходящие заявки и профили получателей |
| POST | `/api/events/{event_id}/invitations` | Создать приглашение |
| GET | `/api/users/{user_id}/invitations` | Действующие входящие приглашения с карточкой события |
| PATCH | `/api/invitations/{invitation_id}` | Принять / отклонить |
| DELETE | `/api/invitations/{invitation_id}?actor_id=UUID` | Отозвать приглашение |

Новые списки принимают `offset >= 0` и `limit` от 1 до 100 (по умолчанию 20).
`kind` по умолчанию `organized`, `direction` — `incoming`.
Списки событий упорядочены по началу и ID, заявок/приглашений — от новых к старым.
Удалённые события не возвращаются. Прошедшие личные события остаются для истории.
Текущий Event API рассчитан на одно проведение события; повторения — отдельная задача.

## Редактирование профиля

```http
PATCH /api/users/USER_UUID
Content-Type: application/json

{"display_name":"Иван","bio":null,"city":"Санкт-Петербург"}
```

Допустимы `username`, `display_name`, `bio`, `avatar_media_id`, `city`, `latitude`,
`longitude`. Пропущенные поля сохраняются, `null` очищает необязательное поле.
Координаты изменяются/очищаются только парой; username и display_name не могут быть
`null`. Пустой patch и неизвестные поля дают 422, занятый username — 409.
Аватар должен быть готовым media asset, принадлежащим этому пользователю.

## Персональные состояния карточки

`GET /api/events?viewer_id=UUID` и `GET /api/events/{event_id}?viewer_id=UUID`
возвращают поле:

```json
{
  "personal_state": {
    "is_favorite": true,
    "is_dismissed": false,
    "participation_status": "REQUESTED"
  }
}
```

Без viewer_id поле `personal_state` равно `null`. В личных списках и календаре
состояние заполняется для указанного пользователя. Флаги независимы: можно
сохранить событие и одновременно иметь заявку или участие.

| participation_status | Состояние интерфейса |
| --- | --- |
| null | Не записан |
| REQUESTED | Заявка отправлена |
| GOING | Иду |
| REJECTED | Отклонено |
| CANCELLED | Отменил участие |

«Не интересно» исключает Event из ленты только при указанном viewer_id,
но не отменяет участие и не удаляет избранное. Событие остаётся доступным
по ID и в соответствующих личных списках. DELETE dismissed восстанавливает
показ; прежняя история отрицательного сигнала не стирается.
`friends_of` влияет только на порядок ленты и не заменяет viewer_id.

Избранное и «Не интересно» добавляются идемпотентно, в том числе при конкурентных
повторах. Серверные FAVORITE_ADD/FAVORITE_REMOVE/NOT_INTERESTED пишутся только
при реальном изменении в той же транзакции. DELETE favorites/dismissed возвращает
обновлённую карточку (200), повтор тоже успешен. Для удалённого Event — 404.
Пакетный контракт `/api/interactions` остаётся отдельной задачей.

## Приглашения

```http
POST /api/events/EVENT_UUID/invitations
Content-Type: application/json

{"actor_id":"ORGANIZER_UUID","invitee_id":"USER_UUID","message":"Присоединяйся!"}
```

`expires_at` необязателен; если указан, нужен будущий момент с часовым поясом.
Приглашать могут организатор, менеджер Event и участники организации с правами
управления, согласно существующему `can_manage_event`. Самоприглашение запрещено.
Обычный участник пока не может приглашать друзей от своего имени.
Приглашения доступны для опубликованных неудалённых событий с SCHEDULED-проведением,
кроме EXTERNAL. Они не резервируют место.

```http
PATCH /api/invitations/INVITATION_UUID
Content-Type: application/json

{"user_id":"INVITEE_UUID","accept":true}
```

`accept:false` отклоняет приглашение. Ответить может только получатель (иначе 403).
Принятие создаёт GOING или переводит REQUESTED/CANCELLED в GOING, проверяя
вместимость под блокировкой проведения. REJECTED не восстанавливается.
Уже идущий пользователь не занимает второе место. Переход участия записывается
в `participation_status_history`; повтор не создаёт лишних переходов.

Повтор отправки действующего PENDING возвращает то же приглашение, не меняя
его сообщение/срок. После DECLINED/REVOKED или истечения срока организатор может
отправить его заново. ACCEPTED нельзя переиспользовать для новой записи после
отмены участия; такой сценарий потребует отдельного решения о повторных приглашениях.
Повтор принятия успешен, пока участие GOING; повтор отклонения/отзыва также успешен.
Просроченные, отозванные и закрытые приглашения принять нельзя (409).
Входящий список содержит только действующие PENDING; принятие сразу убирает
приглашение из списка. После ответа обновите карточку/список участий.

## Проверка и применение

Все изменения используют существующую схему БД; новых миграций нет.
Для проверки в PowerShell из каталога backend:

```powershell
uv sync --locked
.\test-personal.ps1
```

Скрипт требует Docker и готовый образ `dvizh-postgres:latest` (его можно собрать
через `docker compose build postgres` из корня). Он запускает отдельный PostgreSQL
с автоматически удаляемыми тестовыми данными, применяет миграции, выполняет тесты
и останавливает свой контейнер.
Рабочую БД не использует. Проверяемые HTTP-сценарии находятся в
`tests/test_personal_scenarios.py` и `tests/test_personal_edge_cases.py`.
Без TEST_DATABASE_URL интеграционные тесты пропускаются; обычные тесты продолжают работать.

Применить код к локальному запущенному backend из корня проекта:

```powershell
docker compose up -d --build --no-deps backend
```
