# Изображения, жизненный цикл событий и уведомления

Реализованный этап ветки `26-media`: загрузка обложек/аватаров в MinIO,
полностью заполненные черновики, публикация, отмена и уведомления внутри приложения.
Повторения, stories, организации и импорт внешних событий остаются следующими задачами.

## Контракт пользователя

Авторизацию реализует другой разработчик. Как согласовано, пока используются явные
`user_id`, `actor_id` и `viewer_id`. Они задают действующего пользователя, но не
подтверждают его личность. При интеграции авторизации нужно брать их из проверенной
сессии. Доменные проверки владельца/менеджера и принадлежности медиа уже есть.

## Загрузка и назначение изображений

1. `POST /api/media?user_id=UUID&filename=photo.png`: тело содержит **байты файла**,
   `Content-Type: application/octet-stream`. Это не multipart и не JSON/base64.
2. Ответ 201 содержит `id`, размер и размеры изображения, тип и `content_url`.
3. `PUT /api/users/{user_id}/avatar` с `{"media_id":"UUID"}` назначает аватар.
4. `PUT /api/events/{event_id}/cover?actor_id=UUID` с тем же телом назначает обложку.
5. `{"media_id":null}` убирает привязку. Сам объект остаётся для возможного повторного
   использования; замена обложки/аватара не удаляет файлы автоматически.

Пример PowerShell:

```powershell
curl.exe --noproxy localhost,127.0.0.1 -X POST "http://localhost:8080/api/media?user_id=USER_UUID&filename=photo.png" `
  -H "Content-Type: application/octet-stream" --data-binary "@photo.png"
```

Принимаются статические JPEG, PNG и WebP. Фактическое содержимое проверяется Pillow,
ориентация EXIF применяется, метаданные удаляются, изображение сохраняется в WebP.
Максимальная сторона после обработки — 4096 пикселей. SVG, GIF, анимация и повреждённые
файлы отклоняются. Обложку может назначить организатор/менеджер, используя своё READY-медиа;
чужое медиа назначить нельзя. В EventDTO добавлены `cover_media_id`/`cover_url`,
в ProfileDTO — `avatar_url`.

`GET /api/media/{id}/content` отдаёт изображение через backend. MinIO не публикует bucket
и не возвращает секреты или внутренний адрес в URL. Непривязанное изображение доступно
загрузившему его пользователю с `viewer_id`. Аватары активных профилей и обложки
недрафтовых PUBLIC/UNLISTED-событий доступны публично. Обложки FRIENDS доступны друзьям
организатора, PRIVATE — приглашённым/участникам; менеджеры имеют доступ к обложкам
своих событий. Черновик и его непубличная обложка доступны только менеджерам/загрузившему
медиа пользователю. Одно изображение можно использовать в нескольких местах: назначение
его публичным аватаром делает этот файл публично доступным.

Ошибки: 400 — неверный Content-Length, 403 — чужое медиа/нет доступа,
404 — ресурс отсутствует, 409 — медиа не готово или событие закрыто для редактирования,
413 — превышен размер/число пикселей, 415 — неподдерживаемое/повреждённое изображение,
503 — MinIO недоступен. Лимит проверяется и по заголовку, и по полученным байтам.

## Настройки

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| MEDIA_MAX_MIB | 10 | Размер тела загрузки; общий для nginx, web-app и backend |
| MEDIA_MAX_PIXELS | 25000000 | Ограничение числа пикселей до декодирования |
| MINIO_SECURE | false | TLS между backend и MinIO |
| MINIO_TIMEOUT_SECONDS | 10 | Таймаут подключения/чтения SDK |

Публичные ограничения: `GET /api/media/config`. В ответе нет секретов.
Nginx использует официальный envsubst-шаблон; переменная задаётся через Compose.
В web-app React-сборку раздаёт nginx; его envsubst-шаблон использует тот же лимит.
Оба nginx ограничивают обычные и chunked-загрузки до передачи тела в backend.
SDK MinIO и обработка изображений выполняются вне ASGI event loop.

Метаданные и READY-статус фиксируются только после успешной записи объекта. Откат
транзакции вызывает удаление созданного объекта; фиксация завершается до отправки
HTTP-ответа. Аварийное завершение процесса или недоступность MinIO во время компенсации
могут оставить непривязанный объект — для эксплуатации потребуется отдельная периодическая
сверка; автоматически удалять рабочие volumes нельзя.

## Черновики, публикация и отмена

| Метод | Путь | Действие |
| --- | --- | --- |
| POST | `/api/events/drafts` | Создать полностью заполненное DRAFT-событие |
| GET | `/api/users/{user_id}/drafts` | Черновики организатора, offset/limit |
| GET | `/api/events/{id}?viewer_id=UUID` | Получить свой/управляемый черновик |
| PUT | `/api/events/{id}?actor_id=UUID` | Заменить параметры события |
| POST | `/api/events/{id}/publish` | Опубликовать; тело `{"actor_id":"UUID"}` |
| POST | `/api/events/{id}/cancel` | Отменить; такое же тело |
| DELETE | `/api/events/{id}?actor_id=UUID` | Мягко удалить; опубликованное событие сначала отменяется |

Тело создания черновика совпадает с CreateEventDTO: название, начало и организатор
обязательны; OFFLINE требует место, ONLINE — ссылку. Старый `POST /api/events`
по-прежнему создаёт опубликованное событие, сохраняя текущий контракт приложения.

Переходы: DRAFT → PUBLISHED, DRAFT/PUBLISHED → CANCELLED. Повтор публикации уже
опубликованного события и повтор отмены успешны и не создают повторные уведомления.
CANCELLED нельзя опубликовать или редактировать. Публикация ставит published_at;
отмена ставит cancelled_at и отменяет запланированные проведения. Участия сохраняются
для истории, но отменённое событие исчезает из активного календаря, ленты и доступных
для записи событий. Организатор/менеджер необходим для изменения, публикации, отмены,
назначения обложки и удаления. PUT/DELETE теперь требуют actor_id.

## Уведомления

`GET /api/users/{user_id}/notifications?unread_only=true&offset=0&limit=20` возвращает
уведомления от новых к старым. `unread_only` по умолчанию false, limit — 1..100.
`PUT /api/users/{user_id}/notifications/{notification_id}/read` отмечает прочтение;
повтор сохраняет первоначальное read_at. Прочитать чужое уведомление нельзя.

Типы: EVENT_UPDATED и EVENT_CANCELLED. Получатели — активные участники GOING,
ожидающие REQUESTED, пользователи с избранным и действующие приглашённые.
Инициатор исключается, пересечение этих групп не создаёт дублей. Изменение обложки
также уведомляет; изменения черновика и повтор PUT без изменения данных — нет.
Payload содержит название события и список changed_fields, а не всю карточку.
Записи создаются в той же транзакции, что и изменение события. Email, push,
WebSocket и внешний брокер на этом этапе не добавлены.

## Миграция, проверка и запуск

Добавлена миграция `20261014_0003`, создающая только event_notifications.
Старые миграции и volumes не изменяются. Backend применяет Alembic при старте.

```powershell
cd backend
uv sync --locked
.\test-media.ps1
```

Скрипт требует Docker и образы dvizh-postgres/dvizh-minio. Он создаёт отдельные
PostgreSQL и MinIO с автоматически удаляемыми тестовыми данными, проверяет миграции,
HTTP-сценарии personal и media, их совместную работу и Ruff,
затем останавливает только свои контейнеры.
Без TEST_DATABASE_URL/TEST_MINIO_ENDPOINT интеграционные тесты пропускаются.

Проверки React-клиента: `cd web-app; npm ci; npm test; npm run lint; npm run build`.
Прокси проверяется отдельно из корня: `python web-app/tests/test_proxy.py`.
Нужны Python 3.12+, Docker и локальный образ `python:3.12-slim`. Скрипт собирает
тестовые образы nginx/web-app, поднимает отдельную сеть и backend-заглушку,
проверяет маршруты SPA, передачу query-параметров и лимиты тела на обоих прокси.
После проверки удаляет только свои контейнеры, сеть и теги образов.

После объединения веток из корня проекта:

```powershell
docker compose up -d --build --no-deps backend web-app nginx
```

Карточки во всех личных списках и приглашениях включают обложку вместе с personal_state.
Список черновиков также возвращает personal_state организатора. Доступ к самому
черновику сохраняется только для организатора и менеджеров; попытка другого
пользователя добавить его в избранное или скрытые завершается 403 без записи изменений.
