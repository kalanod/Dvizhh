# Карта и лента мероприятий

`POST /api/events/discovery` возвращает карту и ленту. Backend проверяет доступ,
считает подходящие мероприятия и формирует карточки.

## Запрос

```json
{
  "filters": {
    "q": "", "tag_id": null, "date_from": null, "date_to": null,
    "free_only": false, "available_only": false,
    "viewer_id": null, "friends_of": null
  },
  "viewport": {
    "west": 29.9, "south": 59.8, "east": 30.6, "north": 60.1,
    "zoom": 11, "center": {"longitude": 30.3, "latitude": 59.95}
  },
  "sort": "distance", "origin": null, "selection_token": null,
  "cursor": null, "limit": 20, "include_map": true
}
```

Координаты — WGS84; `west > east` означает пересечение меридиана 180°.
Мировая область: `west=-180, east=180`. Нулевая площадь запрещена.
`viewport=null` возвращает ленту без географического ограничения и без карты.
Единый `EventSort` для discovery и `GET /api/events`: `relevance` (интерес к
тематикам по действиям, популярность и свежесть), `novelty` (дата публикации,
пустые значения в конце), `title` (название без учёта регистра, затем исходное
название), `distance` (метры), `start` (начало выбранного проведения).
SQL-правила общие: классы `EventSorting` возвращают типизированные `SortKey`
с направлением, типом значения и сравнением для курсора. Режим друзей сначала
поднимает события с большим числом идущих друзей, затем действует сортировка.

Default API — `novelty`; интерфейс выбирает `relevance` для вошедших и `novelty`
для гостей. При заданном `RECOMMENDATION_GRPC_ADDRESS` Backend получает
`relevance` для вошедших из сервиса рекомендаций. Выбор кластера и режим друзей
обрабатывает Backend. При `distance` точка — центр карты, а при выборе кластера — центр
его исходной области. Без карты передаётся `origin: {longitude, latitude}`;
если его нет, геокодируется город проверенного профиля без сохранения координат. Без точки ответ 422,
автоматической замены сортировки сервером нет. Онлайн-события и места без
координат при отсутствии ограничения области находятся в конце distance-ленты.
Интерфейс сначала запрашивает геопозицию и использует город профиля при отказе;
если обе точки недоступны, сохраняет прежнюю сортировку и объясняет причину.

Личность определяется по проверенной cookie-сессии. Переданные `viewer_id` и
`friends_of` могут совпадать только с текущим аккаунтом, иначе 403. Они не дают
доступ к чужим персональным данным. Гость передаёт `null`. Такое же правило
применяется к параметрам старого GET: новый relevance нельзя использовать
для чтения чужого персонального порядка или состояний через query UUID.

## Ответ и правила отбора

`filters.q` использует общий поиск `EventQueryService` для карты и ленты.
Если весь запрос — один `#хештег`, ищется целый хештег в названии без учёта регистра:
`#поход` не находит `#походы`, `слово#поход` или совпадение только в описании.
Буквы разных языков, цифры и подчёркивания поддерживаются. Остальные запросы
сохраняют полнотекстовый поиск. Хештег в названии — ссылка на `/?q=…`;
переход и история браузера синхронизируют общее поле поиска, карту и ленту.

Ответ: `{as_of, map: {items, total_events} | null, feed: {items, next_cursor}}`.
В обычной ленте «Рекомендуем» `feed.total_events` отсутствует. Для выбранной
группы на карте и других сортировок Backend возвращает счётчик ленты.
Полная схема и ограничения доступны в OpenAPI.
Для страниц из сервиса рекомендаций `feed` содержит `session_id` и `request_id`.
Frontend сохраняет их с полученными карточками для логирования действий.

- Только опубликованные публичные неудалённые события с запланированным
  текущим или будущим проведением. Учитываются поиск, тематика, даты по поясу
  события, цена, наличие мест и персональное скрытие.
- Единица подсчёта — `event_id`. Среди подходящих проведений выбирается текущее,
  иначе ближайшее будущее. Сервис рекомендаций возвращает конкретное проведение;
  Backend проверяет, что оно всё ещё доступно, и показывает именно его.
- При географическом ограничении нужны точные координаты места. События без
  координат и онлайн-события остаются доступны в ленте без области.
- Локальная выдача использует снимок REPEATABLE READ READ ONLY с границей
  отбора `as_of`. Страницы рекомендаций проверяются по актуальному каталогу.
- Карта содержит не более **30 объектов суммарно**. `event` имеет `count=1`
  и `event_id`; `cluster` — `count>1` и `selection_token`. У обоих есть `id`,
  координаты центра и `bounds` фактических точек, иногда нулевой площади.
- Сервер адаптивно делит мировую сетку Web Mercator; SQL агрегирует весь набор.
  LIMIT 31 используется лишь для обнаружения переполнения, после которого
  выбирается более крупная сетка. Отбрасывания событий ради лимита нет.
  Совпадающие точки остаются кластером при максимальном приближении.

Каждый объект карты содержит `state`: `favorite` (жёлтый), `organizer` (красный),
`going` (розовый) или `default` (фиолетовый). Приоритет указан от высшего к низшему.
Состояние считается только для проверенного пользователя; у гостя `default`.
Для группы берётся максимальный приоритет всех входящих событий независимо от
текущей страницы ленты. Участие GOING в любом подходящем проведении помечает
повторяющееся событие, которое всё равно считается один раз.
У одиночного маркера `title` — название события, у группы `title=null`.
Подсказка одиночного маркера: название и на новой строке «В избранном», «Организую»,
«Иду» или «Открыто» согласно выбранному состоянию. У группы — «N движей рядом»
со склонением. Цвет обновляется и у уже существующего маркера после изменения
персонального состояния; координаты и камера при этом не меняются.

Нажатие на кластер передаёт его непрозрачный `selection_token`. Лента фиксирует
пересечение исходной области карты с ячейкой кластера, включая исходный центр
сортировки. Последующее движение карты обновляет её независимо от выбранной
группы. Сброс выбора снова связывает ленту с текущей областью. Изменение фильтров
сбрасывает выбор. Одиночная точка открывает мероприятие.

`next_cursor` — подписанная позиция; передавайте её с теми же фильтрами,
выбором, областью и сортировкой. `include_map=false` позволяет получать следующие
карточки без повторной кластеризации. Для локальной выдачи курсор содержит все ключи порядка,
включая текстовые и пустые значения; `NULLS LAST` одинаково применяется при
сортировке и выборе следующей страницы. Порядок стабилизируется датой и UUID.
Для локального relevance время расчёта и вектор интересов фиксируются в подписанном курсоре;
для distance без карты фиксируется разрешённая точка города профиля/запроса. Изменения
истории и профиля не меняют контекст уже начатого прохода. Изменения самих
событий и живых показателей популярности/числа друзей между запросами всё ещё
могут менять порядок: курсор не является снимком всей выдачи. Собственные
действия в интерфейсе сбрасывают кеш и начинают новый проход.
Для рекомендаций сохраняйте также размер страницы. При недоступности сервиса
или отсутствии данных для персонализации текущая лента продолжится по новизне.
Ранее возвращённые мероприятия исключаются, а страницы по новизне приходят
без `session_id` и `request_id`.
Пока приложение открыто и у ленты есть следующая страница, браузер отправляет `POST /api/events/discovery/refresh`
с текущим `{cursor}` и обновляет его из `{next_cursor}`. Интервал `feed.refresh_after_seconds`
по умолчанию равен 300 секундам. Запрос требует сессии владельца курсора и `X-Dvizh-Account: 1`.
Переход к карточке сохраняет текущую ленту и её фильтры.
При недоступности RecSys курсор Backend продлевается для продолжения по новизне.
После истечения авторизации Backend отвечает 401, и браузер прекращает продление.
Подмена, истечение или несовместимый контекст токена возвращают 409; клиент
сбрасывает выбор/пагинацию и загружает свежую выдачу. Срок токена по умолчанию — 600 секунд.
Ответы имеют `Cache-Control: private, no-store`.

Старый `GET /api/events` сохраняет список DTO, `offset/limit` и отбор по
проведениям, в том числе прошедшим, если период не ограничен. Его сортировки
используют те же классы и формулы. Главная страница обращается только к discovery:
общий набор карты и ленты ограничен актуальными событиями и дедуплицируется.

## Индекс и эксплуатация

Миграция `20261117_discovery_geo` подключает PostGIS, добавляет вычисляемую
`locations.position geometry(Point,4326)` и GiST-индекс. Координаты остаются
единственным источником данных; точка автоматически меняется при их обновлении.
Ограничение области использует индексируемый `ST_Covers`. Образ postgres
содержит PostGIS и сохраняет PostgreSQL 17; существующий volume сохраняется.
На внешней БД расширение должно быть установлено, а миграционной роли нужны
права CREATE EXTENSION либо расширение заранее создаёт администратор.

`DISCOVERY_TOKEN_SECRET` — отдельный секрет подписи длиной от 32 символов.
Задайте одинаковое стабильное значение всем экземплярам backend. При пустом
значении генерируется временный ключ процесса: после перезапуска старые токены
получат 409. Секрет авторизации для этого не используется.

## Клиент

`useEventDiscovery` владеет фильтрами, областью, выбором и страницами.
`EventDiscoveryMap` только управляет SDK, камерой и маркерами; `EventSection`
отображает общую выдачу, а `SortMenu` сообщает контроллеру выбранный порядок.
SDK не выполняет дополнительную кластеризацию.
При первом показе геолокация и SDK загружаются параллельно. `POST
/api/events/discovery/bootstrap` принимает `{filters, origin: {latitude, longitude}}`
и возвращает `{nearest: {event_id, point: {latitude, longitude}} | null}`.
Проверки личности и `Cache-Control: private, no-store` совпадают с discovery.
В запросе нет сортировки, viewport, selection или cursor: ближайшая точка выбирается
по точному географическому расстоянию из `DiscoveryRepository.candidates` без
ограничения области, с теми же фильтрами, видимостью, актуальностью и исключениями.
Онлайн-события и события без координат не являются опорными точками.

`initialDiscoveryCamera` вычисляет камеру по двум точкам и размеру контейнера в
проекции Web Mercator, с учётом перехода через 180-й меридиан и отступами 48 px.
Комфортный масштаб ограничен сверху zoom=12: при близком событии пользователь в
центре, при удалении центр непрерывно смещается в сторону события. Обе точки
вписываются в кадр. Синяя отметка показывает местоположение пользователя и не
входит в лимит 30 маркеров событий. Карта создаётся сразу с выбранной камерой;
до ответа для первой области закрыта заглушкой. Пошагового отдаления нет.

При отсутствии событий используется обычный обзор вокруг пользователя.
При отказе геолокации восстанавливается камера sessionStorage, иначе обзор
Санкт-Петербурга. При ошибке/тайм-ауте bootstrap показывается область пользователя
с сообщением; это не объявляется отсутствием событий. Позиция не пишется в профиль.
Автоматическая геолокация запрашивается один раз за загрузку страницы, включая
переходы SPA. Возврат на ленту и сворачивание/разворачивание сохраняют камеру.
Изменение фильтров во время инициализации отменяет устаревший bootstrap; после
первого показа фильтры не передвигают карту. «Найди меня» явно получает новую
позицию и центрирует карту на ней. Ответы после ухода со страницы игнорируются.

При недоступности карты
лента работает без географического ограничения.
Кнопки «Свернуть» и «Развернуть» плавно скрывают и показывают содержимое блока,
сохраняя экземпляр карты и камеру. Сворачивание снимает ограничение области:
запрос получает `viewport=null`, `include_map=false`, выбор кластера и страницы
сбрасываются. Сортировка distance при этом использует последний центр карты как
`origin`. После разворачивания ограничение текущей областью возвращается,
кластер нужно выбрать заново. Изменения размера скрытого контейнера не меняют
сохранённую камеру. Настройка reduced motion отключает анимацию.

После завершения движения карты запрос откладывается на 300 мс. Кеш в памяти
хранит до 30 полных ответов на 60 секунд с LRU-вытеснением; ключ включает
фильтры, пользователя, камеру, сортировку, выбор и курсор. Запросы объединяются,
отменяются при отсутствии подписчиков, устаревшие ответы не заменяют текущие.
После персональных изменений кеш сбрасывается. События не пишутся в localStorage.
Маркерный слой заменяется согласованно, без объединения разных кластеризаций.

## Проверка

`tests/test_discovery.py` проверяет бюджет объектов, полноту группировки,
совпадающие координаты, границы мира, токены и HTTP-проверки личности.
`tests/test_discovery_integration.py` запускается при `TEST_DATABASE_URL`, только
на отдельной мигрированной PostGIS-базе: реальная кластеризация, keyset-страницы,
повторы, видимость, выбранная область и пересечение меридиана 180°.
