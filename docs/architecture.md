# Границы HTTP и сервисов

FastAPI используется в backend и auth-api. Роутер отвечает за HTTP, сервис — за
операцию приложения, а клиент внешнего сервиса — за протокол провайдера.
Не требуется отдельный сервис для каждого endpoint: операции объединяются по
владельцу данных и правил, а не по URL.

## Правила

- `api/routers/`: пути, Query/body, cookies, заголовки, чтение ограниченного потока,
  HTTP-ответы и перевод результата сервиса в ответ. Здесь нет SQL, JWT-политики,
  выбора провайдера или последовательностей бизнес-операций.
- `api/dependencies.py`: создание сервисов и получение request-scoped транзакции.
  Сервисы не создаются в соседнем роутере; роутеры не импортируют друг друга.
- `api/security.py` backend: извлечение cookie и HTTP-проверки административного
  запроса. `api/dependencies.py` auth-api: адаптер проверки сессии и CSRF-заголовков.
- `api/errors.py`: перевод ошибок сервисов в HTTP-статусы, защита чувствительных
  данных в ответах валидации. Сервисы не выбрасывают FastAPI HTTPException.
- `services/`: бизнес-операции и их координация. Они принимают обычные значения
  и типизированные контракты, не Request/Response/Depends. Чистые Pydantic-контракты
  пока общие для API и сервисов; схемы не подключают роутеры или приложение.
- `database/` и repository auth-api: запросы, блокировки и сохранение. Проверки
  владения, статуса и разрешённых переходов остаются в бизнес-сервисах.
- Транзакцией управляет существующий объект Database/DatabaseService. API-зависимость
  лишь открывает его session-контекст; сервисы одной операции используют одну сессию.

## Решение по каждому роутеру

| Роутер | Владелец операции и граница |
| --- | --- |
| backend `events` | EventService: события, участие, права и переходы состояния. Роутер только принимает фильтры и команды. |
| backend `users` | UserService: профиль и его инварианты. JSON-адаптация UserCreate остаётся схемой API. |
| backend `friends` | UserService: запросы дружбы и допустимые переходы. |
| backend `personal` | EventService/UserService: списки, приглашения, отклики. Cookie-контекст для смены пароля собирается одной зависимостью API. |
| backend `lifecycle` | EventService/NotificationService: публикация, отмена, уведомления. |
| backend `tags` | TagService: публичный каталог. Создание зависимости вынесено из роутера. |
| backend `admin` | TagService: изменение каталога; API security проверяет административный запрос. |
| backend `settings` | SettingsService: документ, разрешённые действия, валидация полей и атомарный batch. Роутер оставляет no-store и передачу контекста. |
| backend `media` | MediaService: загрузка, права на контент, владение/готовность файла и назначение изображений. UserService сохраняет профиль. HTTP-поток читается с ограничением из MediaService, Content-Length и заголовки ответа остаются HTTP-задачами. |
| backend `maps` | MapsService: готовность поиска, выбор ключа/провайдера, параметры поиска и нормализация места. YandexMapsClient: HTTP Яндекса, обработка отказов и удаление ключей из диагностики. |
| backend `system` | Проверка инфраструктуры и ответ о состоянии; отдельный доменный сервис не нужен. |
| auth-api `auth` | AccountService: регистрация, пароль и изменения аккаунта. SessionService: выпуск/проверка JWT и существование аккаунта. Роутер выставляет/удаляет cookies и формирует ответы. |
| auth-api `system` | HTTP healthcheck; отдельной бизнес-операции нет. |

## Чего этот рефакторинг не меняет

Пути, тела, статусы и OpenAPI сохраняются. Не создаются новые зависимости и
универсальные базовые сервисы. Если обработчик уже делегирует одну операцию
существующему сервису, дополнительный слой-обёртка ему не нужен.

Полная привязка `actor_id`, `user_id`, `viewer_id` к проверенной сессии в основных
бизнес-ручках — отдельная незавершённая задача. В частности, `viewer_id` для медиа
по-прежнему передаёт клиент: перенос кода в сервисы сам по себе не устраняет риск
подстановки чужого идентификатора. Не считайте эту часть API полностью защищённой
до внедрения общей проверки действующего пользователя.
