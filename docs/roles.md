# Роли аккаунтов

Глобальные роли хранятся в базе auth-api, отдельно от профилей backend:

- `roles`: UUID `id`, уникальное `name` (`user` или `admin`);
- `accounts.role_id`: обязательная ссылка на одну роль.

Роли менеджера события и участника организации относятся к своим доменным объектам
и не предоставляют глобальных административных прав.

При регистрации и миграции существующих аккаунтов назначается `user`.
Указать роль через публичную регистрацию нельзя.
У аккаунта обязателен уникальный никнейм из 3–50 латинских букв, цифр и `_`.
Регистр никнейма не учитывается. Почта необязательна; если указана, она тоже уникальна.
Вход выполняется по никнейму или почте и паролю.
`GET /api/auth/me` возвращает подтверждённый аккаунт и его текущую роль:

```json
{"id": "account-uuid", "username": "username", "email": null, "role": "user"}
```

Роль читается из базы при проверке сессии. Она не копируется в JWT:
изменение роли действует со следующим запросом без повторного входа.
Роль в frontend предназначена для отображения; серверные проверки доступа обязательны.

При необходимости роль меняется напрямую в базе auth-api через `accounts.role_id`.
Консольных команд и публичных ручек для изменения роли нет.

При первом применении начальных миграций создаётся системный аккаунт **admin / admin**
с ролью `admin` и связанный профиль. Начальный никнейм — `admin`, почта не назначается.
Короткий пароль относится только к начальному аккаунту; требования регистрации не меняются.
Пароль хранится как Argon2-хеш. Повторный запуск миграций не меняет пароль и роль существующего
аккаунта. Откат миграций начального заполнения не удаляет аккаунт и профиль с их данными.
Роли и связь с аккаунтами создаёт миграция auth-api при обычном запуске контейнера.
Для регистрации передавайте `{username, email?, password}`, для входа — `{login, password}`.
`login` принимает никнейм или почту. Пустая почта сохраняется как `null`.
`PATCH /api/auth/me` меняет никнейм и/или почту текущего аккаунта; нужна cookie и
заголовок `X-Dvizh-Account: 1`. Этот запрос не позволяет менять роль.
Для старых аккаунтов миграция создаёт уникальные никнеймы вида `user_<UUID без дефисов>`;
их прежняя почта продолжает работать для входа. Никнейм можно изменить в профиле.
Административные ручки каталога тегов используют роль `admin` из auth-api.

Никнейм для входа хранится в auth-api; в backend-профиле находится его копия.
При редактировании интерфейс сначала сохраняет аккаунт, затем профиль. Если второй
шаг временно недоступен, интерфейс сообщает об уже сохранённых данных входа и позволяет
повторить сохранение профиля. При конфликте ника в старых профилях нужно выбрать другой ник.

Для сервера задайте `AUTH_JWT_SECRET` в `.env`: случайную строку не короче 32 символов.
Без настройки auth-api использует случайный ключ на время процесса. Это позволяет
локальный запуск, но после перезапуска auth-api потребуется повторный вход.
Общедоступного фиксированного ключа по умолчанию нет.
